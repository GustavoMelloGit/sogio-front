# i18n

react-i18next powers translation (English/Portuguese), but no component talks to it directly — everything goes through the custom `useTranslation` hook in `src/i18n/useTranslation.ts`, which exposes a stable `{ t, language, changeLanguage }` interface so the underlying library can be swapped later without touching consumers.

## Rules

- Import `useTranslation` from `@/i18n/useTranslation` — **never** from `react-i18next` directly, even for a "quick" one-off string
- One namespace per module, named after the module folder: `auth`, `error`, `finance`, `property`, `stay`. Nest keys by view/component inside that single namespace file — don't create a new namespace per screen
- `common` namespace is only for strings shared across modules (shell/layout chrome, generic action labels like "view all"). Module-specific copy never goes in `common`
- Never hardcode a locale in formatting calls (`'pt-BR'`, `ptBR`, `new Intl.NumberFormat('en-US', ...)`). Always derive the locale from `language` via `DATE_FNS_LOCALES`/`INTL_LOCALES` in `src/i18n/locale-maps.ts`
- Any string with dynamic content (aria-labels, toasts, counts) uses `t()` interpolation (`{{var}}`), not template literals — screen readers and translators both need the full sentence, not fragments
- `Currency.format` stays on BRL; only pass `{ locale: intlLocale }` so grouping/decimal separators follow the active language
- No new npm dependencies — `i18next`, `react-i18next`, `i18next-browser-languagedetector` already cover this

## Structure

```
src/i18n/
  index.ts            ← i18next init, resources registry (touched by every module PR — see below)
  language.ts          ← Language type, SUPPORTED_LANGUAGES, DEFAULT_LANGUAGE
  useTranslation.ts    ← the only import surface for components
  locale-maps.ts        ← DATE_FNS_LOCALES / INTL_LOCALES / date-format-string maps
  locales/
    en/{common,auth,error,finance,property,stay}.json
    pt/{common,auth,error,finance,property,stay}.json
```

## Do

```tsx
import { useTranslation } from '@/i18n/useTranslation';

const { t, language } = useTranslation(['property', 'common']);

<CardTitle>{t('dashboard.title')}</CardTitle>
<Link aria-label={t('propertyList.viewDetailsAriaLabel', { name: p.name })} />
```

## Don't

```tsx
// Wrong — bypasses the abstraction, breaks the "swap the library later" contract
import { useTranslation } from 'react-i18next';

// Wrong — hardcoded locale, ignores the active language
format(date, 'dd/MM/yyyy', { locale: ptBR });

// Wrong — string built manually instead of interpolated, hard to translate correctly
<span aria-label={`Ver detalhes de ${p.name}`} />;
```

## Running module translations in parallel

Migrating the remaining modules (`auth`, `error`, `finance`, `stay`, plus the rest of `property`) is independent per module and safe to fan out across multiple agents — as long as ownership boundaries are respected.

- **One agent = one module = one branch.** An agent only edits files inside its module's `view/`/`components/` and adds its own `locales/{en,pt}/<module>.json` pair. It never edits another module's files.
- **Shared/central files are off-limits to module agents:** `src/i18n/index.ts`, `language.ts`, `useTranslation.ts`, `locale-maps.ts`, and shell components (`Sidebar.tsx`, `SidebarUser.tsx`, `Page.tsx`). Changes there happen in a separate prep or integration step, not inside a module PR.
- **Shell/nav strings ("Dashboard", "Propriedades", "Reconciliar Estadias", app name/tagline) get translated once, upfront, into `common`, before fanning out** — they don't belong to any single module and shouldn't be duplicated or missed by parallel agents.
- **Every module PR touches `src/i18n/index.ts` exactly once**, in the same mechanical shape (one import pair + one entry in the `resources` object). That keeps the inevitable overlap a trivial textual conflict, not a semantic one — merge PRs one at a time and resolve by re-adding the missing line.
- **Use isolated worktrees per agent** (`Agent` tool `isolation: "worktree"`, or manual `git worktree`) so parallel agents never share a working directory or index.
- **Each module PR is reviewable on its own:** `npm run lint -- --fix` clean, one commit (`feat(i18n): translate <module> module to en/pt`), and a browser smoke check (mock the module's API calls with Playwright, toggle language, screenshot mobile + desktop, confirm no console errors, confirm `<html lang>` syncs and the choice persists after reload) on at least one representative screen — mirrors what was done for the Dashboard pilot.
- **No Architect/Designer pass needed** — translating an already-shipped screen is a content change, not a new feature or layout change (see the Maestro's skip criteria). A quick Accessibility check is still worth it wherever a new interpolated aria-label is introduced.
